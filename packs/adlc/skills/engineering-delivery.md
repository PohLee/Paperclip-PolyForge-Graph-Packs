# Engineering delivery

Use for implementation planning, frontend or backend execution, architecture review, or engineering acceptance.

Read architecture_context and its accepted baseline or reviewed non-applicability rationale. Cite affected invariant IDs and proof in the plan. After planning, record the smallest suitable implementation-shape: backend, frontend, fullstack or parallel. Integrate active branches into one versioned implementation_candidate before independent review. Use the host check runner when configured and preserve its logs.

For complex or high-impact features, require `technical_design_context` at readiness and cite the accepted design and gate decision. For changed permissions, trust boundaries, sensitive data flows or external integrations, also cite the accepted threat model in that design. In readiness, connect each material control to an implementation owner and a verification check. Surface missing or stale analysis for disposition before implementation. Record why the security review is inapplicable for a bounded change. Map planned tickets to the accepted design boundaries, failure modes and verification checks. After implementation, compare the approved design with the pinned code revision through `design-drift`; a mismatch needs a design revision or code correction in its authorized path before the design is treated as current.

1. Pin the approved requirement, design identity, product decisions, and candidate boundaries. Classify feature versus defect. For a defect, finish systematic debugging and preserve a red executable check before the implementation plan. Before the readiness gate, confirm the target branch, planned base revision and working tree state. Read the relevant CI configuration and project scripts to confirm build, test, lint and type-check commands. Inspect the affected interfaces, shared types, persistence and migration rules where relevant. Record the revision, source paths or commands, and any unknowns in the existing readiness report. Challenge readiness and record unresolved decisions and material unknowns for the existing gate. In Paperclip, query the project's Knowledge for relevant `run-lesson` records and check whether their evidence and suggested changes apply to this candidate.
2. Define interfaces and tests in an accepted plan. Use ticket-planning to publish unique ticket IDs, independent deliverables, owners, verification and acyclic blocker edges in the `implementation-plan` output contract. For multi-agent work, use the ticket-planning guidance on integration evidence and write scope before making each delegation decision. Check shared mutable state, independent deliverables, tool conflicts and the integration check. Delegate through the authorized host when the work is independent or requires isolation. Retain the child execution ID, input, output and review evidence.
3. Run the development loop on each slice. Build and test changed behavior, check protected behavior, and review code and test evidence. Record unresolved findings and a concrete rework target.
4. Complete when all active branches and independent review cite the integrated candidate version, the gate decision is recorded, and retrospective observations are linked for future planning. Give the human owner one sourced observation and proposed change for the relevant attempt and candidate when a lesson is worth reusing. A rejected fix returns to classification and root-cause evidence.
