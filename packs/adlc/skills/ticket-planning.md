# Ticket planning

Use after readiness when an implementation plan must be split into executable work. The implementation-plan output contract is the source of truth; see `pack.policyDocuments.evidenceContracts`.

1. Turn accepted behavior into the smallest tickets that each deliver an independently observable result. Name owner, deliverable, verification, and exact blocker IDs. For a wide migration that cannot stay green as a vertical slice, state the expansion, caller batches and contraction dependencies in that order.
   For a cross-layer change, reuse each affected acceptance criterion ID in the plan. Trace the observable behavior through the relevant UI, API, data or business rules and name the check that will prove it. Carry that same ID and the observed proof into the existing acceptance matrix. For a draft that must survive a reload, trace the save request, stored value and reload check under the same criterion.
2. For work split across agents, name the integrated result and the check that proves it for each batch. Then map each ticket's dependencies and expected write scope. Group ready tickets for parallel execution where writes can be integrated independently. Assign one owner to a shared contract, migration, or lockfile edit and place dependent work after it. Verify the actual changed paths before integration and revise the plan if the write scope expands.
3. Validate the ticket graph: unique IDs, known blockers, no cycles. Compute the ready frontier from completed IDs, and dispatch only ready tickets. The host or tracker preserves status and proof; Graph role authority and delegated execution rules still apply.
4. After integration, list every planned ticket once against the pinned candidate with its observed result and evidence reference. Missing or incomplete tickets block the integrated completion contract. Complete when the independent reviewer can trace each finished ticket to the plan and check the actual result.
