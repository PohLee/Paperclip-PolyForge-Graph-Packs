# ADLC lifecycle orchestration

Use when selecting the next workflow or handing work across product, design, engineering, verification, release, and maintenance.

Use system-architecture when establishing or revising system boundaries; otherwise link an accepted architecture baseline or a reviewed non-applicability rationale into implementation. Optionally use code-delivery for sourced PR-head checks and observed merge evidence. Both workflows preserve the separate release process and its human authority.

For a complex or high-impact feature, route the accepted requirement through `technical-design` before implementation and carry its accepted artifact and decision as `technical_design_context`. After implementation, run `design-drift` against a pinned code SHA when the design must remain authoritative. Small bounded changes keep the ordinary route. The host decides applicability and authenticates fresh review sessions and source reads.

Use request-triage for an issue, external PR, or feedback item that needs a sourced ready brief, information request, or closure. A ready report may be linked as `triage_handoff` into the named discovery or implementation Graph; direct approved requests can still enter their existing path.

Use `incoming-request-advisor` before decomposing an unclear ask. Discovery invokes `autonomous-investigation` to classify and source material claims. A risky Epic assumption can enter optional `product-experiment`; an accepted intent enters `requirements-baseline` for a pinned handoff before implementation. An explicitly scheduled market watch can enter `competitive-watch`, whose material result asks for product review without editing scope. The Product Manager may use `feature-investment-advisor` when recommending build, defer, validate or stop choices.

1. Classify the entry: idea, planned feature, clear small change, defect, or production signal. Select only the analysis and planning depth needed to expose material decisions. A clear small change may enter implementation with an already approved requirement; a defect enters root-cause investigation first.
2. Carry a versioned chain: sourced intent, accepted spec and requirement IDs, design identity when needed, accepted implementation plan, code and tests, independent review, fixed-candidate verification, and an acceptance decision. Each handoff names the exact predecessor artifacts and unresolved questions. Complete when no downstream claim depends on an unversioned upstream assumption.
3. Route judgment to its authorized owner and preserve the Decision Record before continuing. An agent may draft, compare, test, and recommend; human product or release authority remains with the authenticated owner where required. Scale review to impact and reversibility while keeping the same evidence chain.
4. After acceptance, connect release evidence and production observations to the candidate. A detected regression or unmet success signal becomes a new sourced intent or defect investigation. Complete the loop when the next run cites the incident, decision history, and affected versions.

The pack executes discovery, requirements, optional experiment and competitive watch, design, implementation, verification, release preparation, release observation, and one-window monitoring graphs. The host supplies the approved product decision after discovery, actual experiment observations, accepted baseline verification, release execution events, production observations, and any pipeline, scheduling, paging, or recovery capability. The release graphs define operational flow and evidence, not complete release certification.
